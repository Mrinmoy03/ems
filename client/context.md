# WorkTrack Employee Dashboard — Project Context

## 1. Product context
WorkTrack is a planned scalable employee management system. The source requirements describe three roles/areas:
- Employee
- Admin
- Super Admin

This phase focuses only on the employee-facing frontend. Future work will add the Admin and Super Admin modules.

## 2. Source of truth
Use these references in this order:
1. The user's provided WorkTrack employee dashboard screenshot for visual direction.
2. The user's `Scalable Employee Management.pdf` for stated functional requirements.
3. This context and the implementation rules for decisions made specifically for the first frontend phase.

Do not silently introduce backend features that have not been requested. If a rule is ambiguous, keep the implementation simple, document the assumption, and isolate it so it can be changed later.

## 3. Functional requirements from the project brief
The employee should be able to:
- Log in; the work timer starts with the session.
- View tasks assigned for the day.
- See deadlines and task status.
- Update progress and mark tasks completed.
- Explain delays for overdue tasks.
- View task statistics, working hours, and performance charts.
- Apply for leave; submission should eventually notify the Super Admin by email.
- Change profile image.
- View daily End-of-Day (EOD) reports and monthly performance reports.
- Add a task to their own task list when they are doing work that was not assigned by an Admin.
- Update progress on tasks spanning multiple days.
- Mark lunch break; the working timer pauses during lunch and resumes when the break ends.
- Log out; the daily EOD report is eventually generated by the backend.

The Admin should eventually be able to create employee accounts, assign tasks to one or more employees, change task deadlines/time settings with reasons, and review employee reports. Only the Super Admin can approve or reject leave requests.

## 4. Important scope decision: deadlines, not allocated time
For this frontend phase:
- Every task can have a deadline.
- The dashboard must **not** show a “Time Allotted” column.
- Do not include an allocated-duration field in the employee task model.
- Do not calculate overdue status from an allocated duration.
- Overdue status is based on an incomplete task passing its deadline.
- Do not remove the working-hours timer: it is a separate attendance feature, not task time allocation.

## 5. Technology stack
Required:
- React
- TypeScript
- Tailwind CSS
- SCSS
- shadcn/ui

Recommended supporting packages:
- Vite — frontend development/build tooling.
- React Router — employee-area navigation.
- Recharts — dashboard charts.
- `lucide-react` — icons.
- `date-fns` — date formatting and date calculations.
- `react-hook-form` and `zod` — forms and validation.
- `@hookform/resolvers` — connect Zod validation to React Hook Form.
- `sonner` — toast notifications.
- `clsx` and `tailwind-merge` — class composition; shadcn projects commonly expose a `cn()` utility using these.

Keep the dependency list lean. Do not add a state-management library unless the application actually needs it; React state and context are enough for this initial module.

## 7. Task model guidance
Suggested frontend type:
```ts
type TaskStatus = "pending" | "in-progress" | "completed" | "overdue";
type TaskProgress = 0 | 25 | 50 | 75 | 100;

interface EmployeeTask {
  id: string;
  title: string;
  category?: string;
  deadline: string; // ISO date-time
  status: TaskStatus;
  progress: TaskProgress;
  isSelfCreated: boolean;
  comment?: string;
  completedAt?: string;
}
```

Do not add `allocatedTime`, `timeAllotted`, or similar fields.

## 8. Working assumptions
- The screenshot's employee name, tasks, schedule, and chart values are illustrative only.
- Use a coherent demo employee and mock tasks.
- The app is frontend-only in this phase; authentication, persistence, email, and scheduled report generation will be integrated later.
- The timer can be interactive in the prototype but cannot guarantee durable attendance records without a backend.
- Leave requests can be created and displayed locally, but approval and email notification are future backend workflows.
- Performance analytics in this phase are visual summaries of mock data, not an official employee score or HR evaluation.
